# Plan features backend (Phase 9A): custom roles, commission, multi-branch, advanced reports
Status: **backend done, NO UI** (9B) · Last updated: 2026-10-06 · Suite `supabase/tests/19_phase9_plan_features.sql` (543) + `20_commission_concurrency.sh`

## Decided with the user
- **Role in use**: `delete_custom_role` refuses with `role_in_use` + member count unless a replacement role is given; then all assignments move in ONE transaction (same branch; a member already holding the replacement there just loses the old one).
- **Commission**: base = invoice LINE net (price x qty - line discount), TAX EXCLUDED. percent = half-up; flat = per unit x qty, capped at the line net. Rule = (appointment's staff, line's service) else the staff default; free-text lines earn only a default PERCENT. Earned only when FULLY paid. Credit note -> proportional reversal (the credit that exhausts the net takes the exact remainder). Payment reversal -> reverses only if the invoice stops being fully paid (then all that is left); a refund after a credit note does NOT reverse twice; fully paid again -> earned again as NEW rows.
- **Report email recipients**: active members holding `reports.view_advanced` at ALL scope, re-checked at send time; revenue only if they also hold `reports.view_revenue` at all scope.

## Commission (..100000, ..170000)
- Tables `commission_rules` (append-only versions: percent | flat(+currency) | none; latest `effective_from <= the day it is earned` wins), `commission_lines` (snapshot taken once when the invoice is first fully paid: pins rule, base, full commission; `feature_off` zero rows when the plan lacks the feature so an upgrade never earns retroactively), `commission_entries` (earn | reversal, reason paid|credit_note|unpaid). All immutable; a BEFORE INSERT trigger keeps each line's balance within [0, full]. RLS select only (`commission_can_see`: view_all at branch/all scope for that branch, or view_own on your own staff profile).
- Engine `commission_sync(invoice)` runs from AFTER INSERT triggers on `invoice_payments` and `credit_notes`, i.e. inside the payment/credit-note transaction under the invoice row lock; it writes only the difference between what the line should hold and what it holds (idempotent). Real parallel proof: `20_commission_concurrency.sh`.
- RPCs: `set_commission_rule(staff,service?,kind,percent_bp?,flat_minor?,currency?,effective_from?)` (`commission.manage_rules` for every branch of the staff + feature), `get_commission_report(biz,from,to,branch?,staff?)` per staff and currency (local dates per branch timezone; view_own sees only self).
- Limits: invoice without an appointment/staff earns nothing; a rule resolved at the moment of full payment.

## Multi-branch (..110000, ..150000)
- RPCs: `create_branch` (optional copy of hours + same-currency prices), `update_branch(branch, patch)`, `archive_branch`, `restore_branch`, `set_primary_branch`, `list_my_branches(biz, include_archived)` (branch switching data: roles per branch, currencies count), `get_combined_overview(biz,from,to)` (per-branch rows + totals PER CURRENCY, archived branches with history included). Create/archive/restore/primary need `settings.business` for every branch + feature `multi_branch`; update needs it for that branch.
- Locks: currency (`currency_locked` invoices, `currency_in_use` appointments/prices), prefix (`prefix_locked` after the first invoice; a prefix used by an ARCHIVED branch is retired for ever: trigger `prefix_retired` 23505 — invoice numbers are unique per business), timezone (`timezone_in_use` with upcoming appointments). Archive refused: primary, last branch, upcoming appointments, open drafts, website uses it (`branch_archive_blockers`, also a trigger for direct updates).
- **Single-branch assumptions** — found in 9A, FIXED in 9B (`20261012090000`, `..100000`): staff profiles / time off / service assignment (only when EVERY branch of the staff member is covered; a profile with no branch yet may be touched by any `staff.manage` holder, because the creation flow needs it), services + categories + custom fields (need the permission for ALL branches; per-branch price/on-off stays with the branch manager), clients (visible/editable with a visit or first booking at a covered branch; clients tied to no branch and with no visits stay visible to Branch-scope holders; Own-scope staff see only theirs), audit log (Owner / All-scope `settings.business` only). Earlier fixes: branches INSERT/UPDATE policies, retired prefixes, scope-aware role guard. Suite `21_branch_scope.sql` proves A-vs-B for owner, manager A, manager Karachi, receptionist, staff (own), a custom role at ONE branch, an all-scope custom role, another business and anon.
- **Known limits (still true, decided to leave):** the public website and the public booking page use the PRIMARY branch only (no location picker; `get_booking_page` accepts a `branch_id` but nothing links to it); a commission rule is resolved at the moment the invoice becomes fully paid (a rule added later never earns retroactively; the snapshot pins it); `branches` SELECT still shows every branch (tax number, prefix) to every member; `report_windows`/`get_basic_report` skip archived branches; SMS credits are one pool per business; `widget_keys` are per business; the Team list used to show "Unknown" for other people because `profiles` RLS lets you read only your own row; FIXED 2026-10-07 by `list_business_member_names` (name + email of the ACTIVE members of your own business only; profiles RLS unchanged).

## Advanced reports (..120000, ..130000, ..180000, ..190000)
- `get_advanced_report(biz, section, period weekly|monthly|custom, anchor?, from?, to?, branch?)` -> `{period{from,to,prev_from,prev_to}, current, previous}`. Weekly = Mon..Sun, monthly = calendar month, custom <= 366 days; previous = the equal period before (month: the month before). Anchor must be <= today+366. Local dates per branch timezone (DST-exact). Needs feature `advanced_reports` + `reports.view_advanced` per branch; money needs `reports.view_revenue`, commission `commission.view_all` + feature; `branches` section also needs feature `branch_comparison`.
- Sections: revenue (per currency: totals, discounts, by payment method, daily trend with every day), staff (appointments, revenue net of credit notes, commission), services (most booked = non-cancelled; highest earning per currency, top 20), clients (active = completed visit, new = first-ever completed visit in window, retention of previous period's clients, bp), appointments (counts + completed/cancelled/no-show rates in basis points), branches (per branch in its own currency, archived included).
- **Scheduled email**: `report_schedules` (weekly = previous Mon..Sun sent Monday `send_hour` local; monthly = previous month on the 1st; local = the branch's timezone or the primary's), RPCs `set_report_schedule(biz, frequency, branch?, enabled, send_hour)` / `delete_report_schedule`, pg_cron `report-schedules` every 15 min -> `enqueue_due_report_summaries()`; claims the period (`last_period_end`) in the same statement, never twice, catches up one period after downtime, a new/re-enabled schedule starts with the NEXT period, skipped (not claimed) while the plan lacks the feature, the business is inactive, or the branch is archived. New outbox event `report_summary` (email to a USER: `message_outbox_push_shape` widened, `outbox_recipient` reads the member's profile email, `outbox_guard` re-checks permission + feature). Edge: `_shared/outbox/report.ts` renders it (English, per-currency lines, previous-period figures); `send_outbox` redeployed. The payload holds revenue figures (30-day outbox retention, super-admin read only).
